# 소싱 파이프라인 개발계획 — 크롤러 앱 + 리스터 앱

작성일: 2026-08-25
상태: 설계 확정, 구현 전

## 1. 목표와 범위

국내 도매/사입 사이트에서 상품을 수집해 내 Shopify 스토어에 등록하는 파이프라인을
만든다. 최종 흐름은 `수집 → 검수 → 등록`이지만, **이번 계획에서 두 앱은 서로를
호출하지 않는다.** 각각 독립적으로 개발하고, 결합점은 파일 하나로 고정한다:
`contracts/product.schema.json`.

크롤러는 그 스키마를 따르는 레코드를 **내보내는 것까지**, 리스터는 그 스키마를 따르는
레코드를 **읽어 Shopify에 올리는 것부터** 책임진다. 두 앱을 이어붙이는 오케스트레이션과
검수 UI는 이번 범위가 아니며, 양쪽이 각자 동작한 뒤에 별도로 설계한다.

### 범위에 포함
- Python 크롤러 앱: 사이트별 어댑터, 수집, 스키마 준수 출력
- Node/TypeScript 리스터 앱: 스키마 입력 → Shopify 상품 생성/갱신
- 두 앱이 공유하는 상품 스키마 계약

### 범위에서 제외 (나중 결정)
- 두 앱을 잇는 큐/DB/스케줄러
- 검수 승인 UI (기존 `apps/dashboard` 재활용 후보)
- 재고·가격 지속 동기화(주기적 재수집 후 갱신)
- 주문 발생 시 도매처 자동 발주

## 2. 리포 구조

```
apps/
  dashboard/     React + Vite 스토어 관리 대시보드 (기존, 목데이터)
  crawler/       Python 수집 앱 (신규)
  lister/        Node/TS 등록 앱 (신규)
shopify-theme/   Shopify 테마 (별개 배포 산출물, 파이프라인과 무관)
contracts/
  product.schema.json   두 앱의 유일한 결합점
docs/superpowers/specs/  설계 문서
```

앱마다 자기 의존성과 실행 명령을 독립적으로 갖는다. 루트에는 공용 워크스페이스 설정을
두지 않는다 — 언어가 섞여 있어 이득보다 제약이 크다.

## 3. 결합점: 상품 스키마

`contracts/product.schema.json` (JSON Schema draft 2020-12). 설계 원칙 세 가지:

1. **원본을 그대로 담는다.** 가격은 도매 공급가(`wholesalePrice`)만 싣고, 판매가 계산·
   마진 규칙은 리스터가 갖는다. 카테고리도 원본 경로만 싣고 Shopify 카테고리 매핑은
   리스터 책임이다. 크롤러가 비즈니스 판단을 하지 않아야 재수집 없이 규칙을 바꿀 수 있다.
2. **모름과 없음을 구분한다.** `stock: null`은 "사이트에서 재고를 알 수 없음",
   `stock: 0`은 "품절"이다. 리스터는 이 둘을 다르게 처리해야 한다.
3. **부분 실패를 표현한다.** 일부 필드 추출에 실패해도 레코드를 버리지 않고
   `warnings`에 신호를 남긴다. 전부 아니면 전무로 만들면 사이트 개편 때마다 수집이 멎는다.

`schemaVersion`은 1에서 시작한다. 호환 불가 변경이 생기면 올리고, 리스터는 모르는
버전을 만나면 처리하지 않고 거부한다.

## 4. 앱 1 — 크롤러 (Python)

### 4.1 스택

- **런타임/패키징**: Python 3.12, `uv` (락파일·가상환경·실행을 한 번에)
- **가져오기**: `httpx` (HTTP) + `selectolax` (HTML 파싱)를 기본 경로로 쓰고,
  JS 렌더링이나 복잡한 로그인이 필요한 사이트에서만 `playwright`로 폴백한다.
  브라우저는 느리고 불안정하니 필요한 어댑터만 지불한다.
- **검증**: `pydantic` v2 모델을 진실의 원천으로 두고, 거기서 JSON Schema를 생성해
  `contracts/product.schema.json`과 일치하는지 테스트로 확인한다. 스키마가 코드와
  따로 놀아 굳는 것을 막는다.
- **테스트**: `pytest` + 저장된 HTML 픽스처

### 4.2 어댑터 구조

사이트마다 마크업과 로그인 방식이 다르므로, 사이트별 코드는 어댑터 하나에 가둔다.

```
apps/crawler/
  src/crawler/
    core/
      fetch.py        HTTP 클라이언트, 재시도, 레이트리밋, 캐시
      session.py      로그인 세션 획득·저장·복원
      pipeline.py     탐색 → 상세 수집 → 정규화 → 검증 → 출력
      models.py       pydantic SourcedProduct (스키마의 원천)
      images.py       이미지 다운로드
      errors.py
    adapters/
      base.py         Adapter 프로토콜
      <site>.py       사이트별 구현
    cli.py
  tests/
    fixtures/<site>/  저장된 HTML — 네트워크 없이 도는 테스트의 근거
```

어댑터가 구현하는 것은 네 개뿐이다:

| 메서드 | 책임 |
|---|---|
| `login(session)` | 필요 시 인증. 불필요하면 no-op |
| `discover(query)` | 검색어/카테고리 → 상품 URL 목록 (페이지네이션 포함) |
| `parse(html, url)` | 상세 페이지 → `SourcedProduct` |
| `id_of(url)` | URL → `sourceId` (중복 판정 키) |

core는 어떤 사이트인지 모르고, 어댑터는 재시도·레이트리밋·출력 형식을 모른다. 사이트가
개편되면 고칠 파일이 하나로 특정된다.

### 4.3 인증

국내 도매 사이트는 대부분 로그인해야 도매가가 보인다. 계정 정보는 코드·리포에 절대 두지
않고 `.env`(gitignore)와 환경변수로만 받는다. 로그인 후 쿠키는
`apps/crawler/.sessions/<site>.json`에 저장해 재사용하고, 만료를 감지하면 한 번만
재로그인한다. 매 실행마다 로그인하면 계정 잠금 위험이 커진다.

### 4.4 수집 파이프라인

```
discover → (중복 스킵) → fetch 상세 → parse → validate → 이미지 다운로드 → write
```

- **중복 스킵**: `(site, sourceId)` 기준. 출력 디렉터리의 기존 레코드를 색인해 판단하며,
  `--refresh`로 무시할 수 있다.
- **레이트리밋**: 어댑터별 동시성 상한과 요청 간 간격을 설정으로 강제한다. 기본은
  동시 2, 요청 간 1초. 상대 서버에 부담을 주지 않는 선을 기본값으로 둔다.
- **재시도**: 네트워크 오류와 5xx만 지수 백오프로 3회. 4xx는 재시도하지 않는다 —
  대개 코드나 세션 문제이며 재시도해도 같은 결과다.
- **HTTP 캐시**: 개발 중 같은 페이지를 반복 요청하지 않도록 응답을 디스크에 캐시한다.
  파서를 고치는 동안 사이트를 다시 때리지 않기 위한 것이다.

### 4.5 출력

```
apps/crawler/out/<site>/<날짜>/products.jsonl   레코드 한 줄에 하나
apps/crawler/out/<site>/<날짜>/images/<sourceId>/<n>.<ext>
apps/crawler/out/<site>/<날짜>/run.json         실행 요약: 성공/실패/스킵 수, 오류 목록
```

JSONL은 append 가능하고 중간에 끊겨도 앞부분이 살아남는다. 실패한 레코드는 출력에서
빠지되 `run.json`에 URL과 원인이 남아 재시도 대상을 특정할 수 있다.

### 4.6 CLI

```
crawler login <site>
crawler discover <site> --query "..." [--limit N]      URL 목록만 출력 (파서 없이 확인)
crawler scrape <site> --url <URL>                      단건 수집, 결과를 stdout으로
crawler run <site> --query "..." [--limit N] [--refresh]
crawler validate <path.jsonl>                          스키마 검증만
```

`discover`와 `scrape`를 분리해 둔 이유는 개발과 디버깅 때문이다. 사이트가 개편되면
탐색이 깨진 건지 파싱이 깨진 건지 한 번에 가른다.

### 4.7 테스트 전략

파서 테스트는 **네트워크에 나가지 않는다.** 실제 상세 페이지 HTML을
`tests/fixtures/<site>/`에 저장해 두고 그것으로 `parse()`를 검증한다. 픽스처는 정상 상품,
옵션 다중 상품, 품절 상품, 이미지 없는 상품 네 가지를 최소로 갖춘다. 사이트가 개편되면
픽스처를 새로 뜨고 테스트가 깨지는 것을 보고 고친다 — 이것이 개편 감지 수단이기도 하다.

core의 재시도·레이트리밋은 가짜 트랜스포트로 테스트한다. 실제 사이트를 때리는 테스트는
`@pytest.mark.live`로 격리해 기본 실행에서 제외한다.

### 4.8 단계별 계획

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| C1 | `uv` 프로젝트 생성, pydantic 모델, 스키마 생성·대조 테스트 | `contracts/product.schema.json`과 모델이 일치함을 테스트가 증명 |
| C2 | core: fetch(재시도·레이트리밋·캐시), errors | 가짜 트랜스포트 테스트 통과 |
| C3 | 어댑터 프로토콜 + 첫 사이트의 `parse()` (픽스처 기반) | 저장된 HTML 4종에서 유효 레코드 생성 |
| C4 | 로그인/세션 저장·복원 | 실제 사이트에 로그인해 도매가가 보이는 HTML 획득 |
| C5 | `discover` 페이지네이션 | 검색어로 상품 URL N개 수집 |
| C6 | 이미지 다운로드, JSONL·run.json 출력 | `crawler run`으로 실제 상품 20건 수집 성공 |
| C7 | 두 번째 사이트 어댑터 추가 | core 수정 없이 어댑터 파일만 추가해 동작 — 경계가 옳았음의 증거 |

C7이 실질적 검증 단계다. 두 번째 어댑터를 붙이며 core를 고쳐야 한다면 추상화가 틀린 것이고,
그때 고치는 편이 사이트 다섯 개를 붙인 뒤보다 싸다.

## 5. 앱 2 — 리스터 (Node/TypeScript)

### 5.1 스택

- Node 22, TypeScript, ESM
- **Shopify Admin GraphQL API** (2025-10 이상). REST Admin API의 상품 엔드포인트는
  이미 레거시이므로 처음부터 GraphQL로 간다.
- `@shopify/admin-api-client` (요청·인증), `zod` (입력 검증), `vitest` (테스트)
- 커스텀 앱 액세스 토큰 방식. OAuth·앱스토어 배포는 하지 않는다(내 스토어 전용).

### 5.2 책임 경계

리스터는 크롤링을 모른다. 입력은 오직 스키마를 따르는 JSONL이다. 하는 일은 넷이다.

1. **검증** — `product.schema.json` + zod로 입력을 거른다. `schemaVersion`이 모르는
   값이면 처리하지 않는다.
2. **변환** — 도매가 → 판매가, 원본 카테고리 → Shopify 카테고리/태그, 원본 HTML → 정제된
   설명. 이 규칙 전부가 리스터 안에 있고 설정 파일로 뺀다.
3. **업로드** — 이미지 업로드 후 상품 생성/갱신.
4. **기록** — 무엇을 어떤 소스에서 만들었는지 남긴다.

### 5.3 가격·변환 규칙 (`apps/lister/config/rules.json`)

```
판매가 = ceil((공급가 × 배수 + 고정비) / 라운딩) × 라운딩
```

카테고리별 배수 오버라이드, 최저 마진 하한, 원 단위 라운딩(예: 100원)을 지원한다.
규칙은 데이터이지 코드가 아니다 — 마진을 바꾸려 코드를 고치게 만들지 않는다.

설명 HTML은 화이트리스트 방식으로 정제한다. 도매 사이트 상세 설명에는 도매처 연락처,
외부 스크립트, 깨진 이미지 링크가 섞여 들어오므로 허용 태그만 남기고 나머지는 버린다.

### 5.4 멱등성 — 가장 중요한 설계 결정

같은 입력을 두 번 돌려도 상품이 두 개 생기면 안 된다. 상품 생성 시 metafield에 출처를
새긴다:

```
namespace: "sourcing"
key:       "source_key"
value:     "<site>:<sourceId>"
```

등록 전 이 metafield로 조회해 있으면 갱신, 없으면 생성한다. 로컬 매핑 파일이 아니라
Shopify 자체에 키를 두는 이유는, 로컬 상태가 유실되거나 다른 머신에서 실행돼도
중복이 생기지 않기 때문이다.

기본 등록 상태는 **DRAFT**다. 크롤링 데이터를 검수 없이 공개하지 않는다. 공개는
`--publish` 플래그로 명시할 때만 한다.

### 5.5 변형(variant) 매핑

Shopify는 상품당 옵션 3개까지이며 변형 수에도 상한이 있다. 스키마의
`options`/`optionValues`를 그대로 매핑하되, 한도를 넘으면 등록하지 않고 실패로 기록한다.
임의로 잘라내면 조용히 잘못된 상품이 올라간다. (정확한 변형 상한은 구현 시점의 API
버전 문서로 확인한다.)

`stock: null`(모름)은 재고 추적을 끄고 올리고, `stock: 0`은 재고 추적을 켠 상태로 0을 넣는다.

### 5.6 API 레이트리밋

Shopify GraphQL은 쿼리 비용 기반 리키버킷이다. 응답의
`extensions.cost.throttleStatus`를 읽어 남은 예산에 맞춰 다음 요청을 늦춘다. 429를
받고 나서 물러서는 방식보다 안정적이다. 대량 등록은 순차 처리를 기본으로 하고, 동시성은
필요할 때만 소폭 올린다.

### 5.7 CLI

```
lister validate <path.jsonl>
lister plan <path.jsonl>              무엇이 생성/갱신/스킵될지, 계산된 판매가와 함께 출력 (호출 없음)
lister push <path.jsonl> [--publish] [--limit N]
lister report <runId>
```

`plan`이 있는 이유는 되돌리기 어려운 작업이기 때문이다. 실제 스토어에 쓰기 전에 무엇이
일어날지 먼저 보여준다.

### 5.8 테스트 전략

Shopify API는 기록된 응답으로 테스트한다(실제 호출 없음). 커버할 것:
가격 규칙 계산, 옵션/변형 매핑, HTML 정제, 멱등 판정(기존 상품 있음/없음), 레이트리밋 백오프.

실제 API를 때리는 확인은 **개발 스토어**에서만 수동으로 한다. 자동 테스트가 실제 스토어에
쓰는 일은 없어야 한다.

### 5.9 단계별 계획

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| L1 | TS 프로젝트, 스키마 → zod 타입, `validate` 명령 | 유효/무효 JSONL을 정확히 가름 |
| L2 | 가격·카테고리·HTML 정제 변환기 | 단위 테스트 통과 |
| L3 | `plan` 명령 (API 호출 없이 전체 계획 출력) | 샘플 20건의 판매가·동작이 표로 나옴 |
| L4 | Admin GraphQL 클라이언트 + 커스텀 앱 토큰 인증 | 개발 스토어 상품 조회 성공 |
| L5 | 이미지 업로드 + 상품 생성 (DRAFT) | 개발 스토어에 상품 1건이 이미지 포함 생성 |
| L6 | metafield 기반 멱등 갱신 | 같은 파일 두 번 실행 → 상품 수 그대로, 갱신만 발생 |
| L7 | 레이트리밋 대응, `push --limit`, `report` | 개발 스토어에 50건 연속 등록 성공 |

L6은 반드시 L7 앞에 온다. 중복 방지 없이 대량 등록을 먼저 하면 정리 비용이 개발 비용보다 커진다.

## 6. 개발 순서

두 앱은 독립이므로 병렬 개발이 가능하다. 다만 **L3(`plan`)까지는 크롤러 없이 진행할 수 있다** —
스키마를 손으로 작성한 샘플 JSONL 몇 건이면 충분하다. 이렇게 하면 리스터 개발이 크롤러 완성을
기다리지 않는다.

권장 순서:

1. `contracts/product.schema.json` 확정 (완료)
2. 손으로 만든 샘플 JSONL 3~5건 작성 → 리스터 L1~L3의 입력
3. 크롤러 C1~C6과 리스터 L1~L7을 병렬로
4. 크롤러 실제 출력으로 리스터를 돌려보고 스키마의 빈틈을 확인
5. 그 시점에 연결 방식(검수 UI/DB/스케줄러)을 별도로 설계

## 7. 운영·법적 고려

- **계정 정보는 리포에 넣지 않는다.** `.env`만 쓰고 gitignore에 포함한다.
- 도매 사이트 이용약관과 `robots.txt`를 어댑터 추가 전에 확인한다. 거래 관계가 있는
  사입처라도 자동 수집이 약관상 허용되는지는 별개 문제다.
- 레이트리밋 기본값을 보수적으로 두고 낮추지 않는다. 계정 차단은 복구가 어렵다.
- 수집한 이미지·설명의 재사용 범위는 도매처마다 다르다. 판매 페이지에 그대로 쓰기 전에
  각 사이트 정책을 확인한다.
- Shopify 등록 기본값은 DRAFT다. 공개는 항상 명시적 결정이어야 한다.

## 8. 열린 질문 (구현 착수 전 결정 필요)

4. 이미지 저장을 로컬 파일로 유지할 것인가, 초기부터 별도 스토리지를 쓸 것인가.
